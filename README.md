# Mi CV con IA — Backend & AI orchestration

Backend, adaptive questioning engine, AI orchestration, and server-rendered
HTML/PDF résumé for **Mi CV con IA**, a Spanish-language AI résumé builder.

The frontend exists as a **Pencil design** (`aiCV.pen`); this repo provides the
API the designed screens consume. See [`CLAUDE.md`](./CLAUDE.md) for architecture,
conventions, and safety rules.

## Quick start (online-only)

> **This app cannot run offline.** The offline backends (`AI_PROVIDER=mock`,
> `PERSISTENCE=memory`) are rejected at startup (`ONLINE_ONLY` in `lib/env.ts`),
> and a runtime connectivity guard in `middleware.ts` returns **503** on every
> request when the host has no network. You must configure Azure OpenAI + Supabase.

```bash
npm install
cp .env.example .env.local          # then fill in the AZURE_OPENAI_* values + Supabase URL/keys
npm run dev                          # http://localhost:3000
```

Required env: `AI_PROVIDER=azure` + `AZURE_OPENAI_API_KEY` / `AZURE_OPENAI_BASE_URL`, and
`PERSISTENCE=supabase` + `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`
(see `.env.example`). Booting without them, or running with no connection, fails fast.

## Web UI

Open <http://localhost:3000> and click **Crear mi CV**. The app walks you through
adaptive questions, shows evidence-backed skill suggestions to confirm, then shows
an **editable review** where you can change anything you typed (objective, personal
info, education, experience, skills) before generating. After it's generated you land
in a **résumé workspace**: the AI analyzes the résumé, lists strengths and **targeted
follow-up questions** to fill gaps (missing languages/interests, thin experience,
etc.), and you answer them inline and **regenerate** — an iterative back-and-forth
that keeps improving the résumé. Finally you download the PDF. Supabase auth is
always required, so unauthenticated users are sent to `/login` (email + password).

> **Honesty:** the AI makes wording stronger and draws out real detail, but it does
> not fabricate or inflate facts (no invented metrics, employers, or achievements).

> The résumé wording is generated by an Azure OpenAI deployment
> (`AI_PROVIDER=azure`), which produces polished, semantically-inferred output from
> your confirmed facts.

## Try the flow

```bash
# 1. Create a profile
curl -sX POST localhost:3000/api/resume-profiles | jq .data.profile.id

# 2. Answer the next question (repeat, following data.nextQuestion.questionId)
curl -sX POST localhost:3000/api/resume-profiles/<id>/answers \
  -H 'content-type: application/json' \
  -d '{"questionId":"career_goal_target","section":"career_goal","rawAnswer":"Asistente administrativa"}'

# 3. Generate + preview + export
curl -sX POST localhost:3000/api/resume-profiles/<id>/generate
open localhost:3000/api/resume-profiles/<id>/resume/preview   # HTML preview
curl -sX POST localhost:3000/api/resume-profiles/<id>/export-pdf -o cv.pdf
```

## Going live

### Use your own Azure OpenAI resource

In `.env.local`:

```bash
AI_PROVIDER=azure
AZURE_OPENAI_API_KEY=...          # your key — stays server-side, never sent to the browser
# The v1 endpoint of your resource. The trailing /openai/v1 is REQUIRED: that surface
# speaks plain OpenAI wire format, so no api-version parameter is needed. Checked at startup.
AZURE_OPENAI_BASE_URL=https://<your-resource>.cognitiveservices.azure.com/openai/v1
AZURE_OPENAI_MODEL=gpt-5.3-codex  # the DEPLOYMENT name; gpt-5-mini / gpt-5-nano for lower cost
```

Restart the server. Confirm it's active at <http://localhost:3000/api/health>
(`"aiProvider":"azure"`). Now generation and analysis run on the real deployment.

Calls go to the **Responses** API (`lib/ai/azure-openai-provider.ts`) — the only
surface the `*-codex` models are served on — with `store: false`, so Azure does not
retain the text people write about their own work history. Per-call token usage,
reasoning tokens and an estimated cost are logged as `[ai-usage]`; the rates behind
that estimate live in `lib/ai/pricing.ts` and should be checked against your own
Azure agreement.

### Résumé guidelines (what "good" means)

The AI follows [`resume-guidelines.md`](./resume-guidelines.md) (project root) when it
**writes** and **analyzes** the résumé — length, tone, action verbs, sections, what to
avoid, etc. Edit that file to change the rules; changes take effect on the next
generation (no restart needed). These are style/format guidelines only — the
factuality rules always win, so the AI won't fabricate even if the file asks it to.

### Going live

Set in `.env.local`:

- `AI_PROVIDER=azure` + `AZURE_OPENAI_API_KEY` + `AZURE_OPENAI_BASE_URL` (and optionally `AZURE_OPENAI_MODEL`)
- `PERSISTENCE=supabase` + `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
  `SUPABASE_SERVICE_ROLE_KEY`
- Apply `supabase/migrations/0001_init.sql` to your Supabase project.
- Optional analytics: `AMPLITUDE_API_KEY`.

Secrets without the `NEXT_PUBLIC_` prefix are **server-only** and never sent to the browser.

## Branding (Rumbo Latino ⇄ Aprende Institute)

One build serves two marketing brands, chosen per request from the request host.
Only marketing changes — colours, typography, header, landing copy, logo, favicon.
The funnel, the AI, the résumé and the database are identical.

**To switch brands, see [`docs/switching-brands.md`](docs/switching-brands.md).**
The one-line version:

```bash
DEFAULT_BRAND=aprende            # previews, localhost, unclaimed domains
```

…then redeploy. But note the rule that catches everyone out:

> `DEFAULT_BRAND` is only the fallback for hosts **no brand claims**. On a domain a
> brand already owns (`rumbolatino.com`, `aprende.com`, …) the host wins and
> `DEFAULT_BRAND` does nothing — use `BRAND_HOST_OVERRIDES=host=brandId` there.
> That precedence is what lets one deployment serve both domains at once.

`<html data-brand="…">` on any page names the brand that actually rendered. Append
`?brand=aprende` to any URL to preview the other brand without changing config.
Design and internals: [`docs/branding.md`](docs/branding.md).

## API

```
POST   /api/resume-profiles                         GET /api/resume-profiles
GET    /api/resume-profiles/:id                      PATCH /api/resume-profiles/:id
POST   /api/resume-profiles/:id/answers
GET    /api/resume-profiles/:id/next-question
GET    /api/resume-profiles/:id/completeness
POST   /api/resume-profiles/:id/education            PATCH/DELETE /api/education/:entryId
POST   /api/resume-profiles/:id/experience           PATCH/DELETE /api/experience/:entryId
POST   /api/resume-profiles/:id/skills/suggest
POST   /api/skills/:skillId/confirm | reject         PATCH /api/skills/:skillId
POST   /api/resume-profiles/:id/generate
POST   /api/resume-profiles/:id/regenerate-section
GET    /api/resume-profiles/:id/resume               GET /api/resume-profiles/:id/resume/preview
POST   /api/resume-profiles/:id/export-pdf
```

Responses use `{ data }` on success and `{ error: { code, message, details? } }` on error.
